Project TRACE — How it works, end to end

This document is the canonical reference for Project TRACE (Tracking, Routing, and Automated Credential Engine) for the Pamantasan ng Lungsod ng Pasig (PLP) Registrar's Office. It outlines the core digital workflow, the Command-Center UI architecture, manual payment verifications, and Machine Learning forecasting.

Design principles & UI Mandates

Fluid "Command-Center" Layouts

Dashboards must maximize screen real estate. We do not use constrained white-space containers. The UI relies on fluid CSS grids spanning the full viewport to present dense, engaging KPIs.

Manual Payment Gate

Payments bypass automated gateways. Students scan a static GCash QR, then upload the receipt and reference number. Finance Clerks manually verify these before routing documents.

Automation over data entry

Clerks do not type what a computer can read. Python EasyOCR extracts Student Numbers and Document Types from uploaded forms via a split-screen verification modal.

Predictive Management

The system uses Prophet & Random Forest ML to forecast volume spikes, alerting the Admin via an aesthetically pleasing dashboard with actionable cards.

1. The Tech Stack & Justifications

Project TRACE utilizes a decoupled microservice architecture tailored for high-density, real-time interfaces.

  • React.js (Vite) + Tailwind CSS: Drives the responsive, fluid-width command-center dashboards. Uses Lucide icons and soft pine-green branding constraints.
  • Node.js + Express.js (Backend API): Securely handles uploads, routing, and serves static files (like receipt uploads).
  • Python, Flask, & EasyOCR: Deep Learning AI microservice. Reads messy, physical academic documents during Window 1 intake.
  • Python, Prophet, & Scikit-Learn: The analytical brain generating 7-day volume forecasts and prescriptive process recommendations.
  • MySQL (Database): Source of truth, logging every state change timestamp for ML training.

3. Student Portal & 3-Column Layout

The citizen-facing side is heavily optimized for aesthetics and usability, moving away from boring standard forms.

  • Unified Layout: The view uses a responsive 3-column grid. The tracker spans two columns, while the submission form sits comfortably in a sticky side-column.
  • Visual Tracking: Progress is indicated by visual bars (amber, blue, pine green) and dynamic status badges, giving the student immediate visual feedback.

4. Command-Center Clerk Dashboards

The primary work surfaces for all Clerks utilize the full width of the screen to present dense, actionable data.

  • Top-Level KPIs: Dashboards feature prominent metrics at the top (e.g., "Scanned Today", "Pending Verification") to provide instant situational awareness.
  • Interactive Queues: Clean, borderless tables with hover-states that reveal quick-action buttons (Approve/Reject/Release) without cluttering the screen.

5. The Manual Payment Workflow

To comply with university restrictions on third-party payment gateways, TRACE utilizes a secure manual verification pipeline.

Workflow

When a student initiates a request, the UI presents a static GCash QR code belonging to the PLP Finance office. The student pays via their app, then uploads a screenshot and inputs the Reference Number into TRACE. The Node.js backend flags the document as PENDING_PAYMENT_VERIFICATION. It sits in the Finance Clerk's dashboard until they manually confirm the transaction against their records and click "Approve."

6. Split-Screen OCR Evaluation (AI)

When the College Secretary clicks a pending document, it triggers the Evaluation Modal.

The modal locks the background and presents a split-screen view. The left side displays the original scanned image with simulated AI bounding boxes. The right side displays the extracted data (Student ID, Name, Type) alongside an AI Confidence Score. The Secretary verifies the fields and clicks "Approve & Route".

7. Predictive Analytics & Admin Tools

The Registrar Admin view is a dedicated analytics and operations command center.

  • Prophet Volume Forecast: A visual chart predicting incoming document volume over the next 7 days, highlighting peak rush days.
  • AI Insights Panel: A dark-themed card utilizing Random Forest heuristics to output prescriptive, plain-English advice (e.g., "Expect a 200% surge... Temporarily reassign staff to Window 1.").
  • Student Verification Desk: A list of pending student account registrations where EasyOCR auto-verification failed. Admins inspect the uploaded ID proofs and manually click "Verify" or "Reject".

8. Frequently Asked Questions (Dev)

  • How do we add a new document type to the system?

    You must update the array of accepted document types in the React frontend (e.g., const DOCUMENT_TYPES = [...]). You must also ensure the backend schema validation accepts the new string.

  • Why aren't we using PayMongo/Xendit?

    As this is a capstone/thesis implementation, acquiring live production API keys for payment gateways requires valid business registrations and school bank accounts. The Manual QR Verification flow securely simulates this process while demonstrating complex state management and role-based approvals.

  • How is the Random Forest ML model retrained?

    The model requires fresh historical data to improve its bottleneck predictions. A scheduled cron job should run monthly, triggering the Python analytics service to fetch the latest timestamps from the step_logs MySQL table, retrain the model, and save the updated `.pkl` file.

9.2 Codebase Architecture

The codebase follows a strict layered folder schema. The full rules live in docs/CODING_PREFERENCES.md and CLAUDE.md; this is the shape.

backend/src/
  config/        Environment variables (env.js), MySQL pool (db.js)
  controllers/   HTTP req/res only — no business logic
  middlewares/   auth (JWT), upload (multer), errorHandler
  models/        Raw parameterized SQL, one function per query
  routes/        URL -> controller wiring only
  services/      Business logic: auth, documents (the pipeline),
                 notification (SMS/email/in-app), aiEngine, n8n
  utils/         AppError helpers, pricing (calculateAmount)

frontend/src/
  assets/        Images and static files
  components/    Reusable UI only — never calls an API
  features/      One folder per role: student, finance, window1,
                 secretary, admin — each owns its modals AND its
                 own use<Role>Dashboard hook
  hooks/         useAuth, useDashboardCore, useAuthedFile
  layouts/       Layout.jsx (header, sidebar, notifications)
  pages/         Route components: Login, Signup, Dashboard
  services/      api.js (axios instance), authService, documentsService
  store/         Intentionally empty — no Zustand/Redux, see below
  utils/         formatters, documentStatus, env
Three Non-Negotiable Rules

1. UI components never call APIs directly — all calls live in services/. 2. Controllers only handle req/res; logic belongs in services/. 3. Never hardcode secrets, not even as a || fallback — read .env through src/config/env.js and document every variable in backend/.env.example.

Multi-Document Requests

A student may request several document types at once. Each becomes its own documents row under a shared request_group_id: payment is per group (one GCash receipt settles all of them), while routing is per document, so a Diploma can reach Window 1 while a Transcript is still with the Secretary. A single-document request is simply a group of one, so all pre-existing behaviour is unchanged.

Configured, Not Coded

Document types, colleges, fees and the Graduate Application's fields live in database tables rather than in source. The Registrar can add a document type, change a fee, or add a form question without a deploy — and the graduate form's validation is generated from its field definitions, so it follows automatically. Fees are always recomputed server-side; a client-supplied amount is ignored.

Deletion Is Deactivation

No maintenance endpoint hard-deletes. Documents reference document types by name and users reference colleges by name, so removing a row would orphan historical records in a system of record. is_active hides an entry from new requests while leaving history intact and restorable. A document type already in use cannot be renamed, and an admin cannot deactivate their own account.

Reporting & Export

The report rows, their summary totals and the CSV export share a single filter object, so what is exported always matches what is on screen. utils/csv.js is written by hand: it escapes commas, quotes and newlines, neutralises spreadsheet formula injection, and the response carries a UTF-8 BOM so Excel renders accented names correctly. Efficiency analytics derive entirely from the step_logs audit trail; per-clerk figures are reported as workload distribution, never as a performance score.

Payments

Four methods — GCash, Credit/Debit Card, Online Banking and Over-the-Counter — each an admin-managed row with its own instructions and reference label. All resolve to the manual provider: the student pays out-of-band and a Finance Clerk verifies against PLP's own records, because payments must reconcile with Finance's books rather than a third party's dashboard. A provider registry in services/payment/ means a hosted gateway can be added later without changing the document pipeline.

Real-Time Notifications

Socket.IO shares the HTTP server, so there is no extra port. Socket.IO supplies no authentication, so the handshake token is verified against the same JWT_SECRET as the REST API and each socket joins only its own user:<id> and desk rooms — a connection can never receive another account's notifications. Measured latency from a student's payment submission to the Finance clerk's dashboard is 55 ms. If realtime is unavailable the notification is still stored and appears on the next fetch, so a socket fault can never affect a desk action.

Testing

Vitest runs per package: cd backend && npm test and cd frontend && npm test (438 tests, no database needed — the model layer is mocked). Backend tests must use the .cjs extension: the source is CommonJS, and only a CJS test shares Node's require cache with it, which is what makes the model spies actually intercept. node backend/audit.js runs a live end-to-end audit through all five desks.

Why store/ is empty

No Zustand/Redux is installed. State is already centralized in useAuth and the per-role feature hooks rather than prop-drilled, so a store would add a dependency without solving an existing problem. Introduce one only when a genuine cross-component state need appears.

9.3 Technical Rollout Phases

  1. Phase 1: Foundation & Upload Pipelines

    Establish the core backend routing, database schemas, and file upload systems (Multer/S3) for both Scans and GCash Receipts.

    • Initialize the MySQL documents and step_logs database schemas.
    • Build the Node.js API endpoints for document submission and the manual Finance approval flow.

  2. Phase 2: UI & OCR Microservice

    Build the React (Vite) dashboards and connect the Python AI.

    • Deploy the Python Flask microservice hosting the PyTorch EasyOCR model.
    • Develop the interactive Role Gateway and fluid Tailwind grids for all clerk dashboards.
    • Implement the Split-Screen Evaluation Modal, binding the right-side inputs to the OCR API JSON response.

  3. Phase 3: ML Integration & Load Testing

    Activate predictive analytics and ensure high concurrency handling.

    • Deploy the Prophet volume forecasting model and Random Forest insight generator for the Admin dashboard.
    • Set up scheduled cron jobs for continuous ML model retraining based on new step_logs timestamp data.

  4. Phase 4: Architecture Restructure & Hardening

    Migrate the organically-grown codebase into the strict layered schema in 9.2.

    • Decompose backend/routes/*.js into route → controller → service → model layers under backend/src/.
    • Split the ~2,000-line DashboardPage.jsx into five per-role components under frontend/src/features/, leaving the page as a thin role dispatcher.
    • Extract notification, AI-engine, and n8n integrations into dedicated services that fail soft, so an outage in an optional service never rolls back a document action.
    • Remove the hardcoded UniSMS fallback secret; centralize configuration in src/config/env.js and document it in .env.example.

  5. Phase 5: Security Hardening & Automated Testing

    Close the authorization gaps found by probing the running system, and pin every fix with a test.

    • Fixed an IDOR allowing any student to attach a payment receipt to another student's request, and stopped uploadDocument trusting a client-supplied student_id.
    • Closed two fully-open machine-to-machine endpoints (/documents/assign and the payment webhooks) behind a shared WEBHOOK_SECRET header.
    • Replaced world-readable /uploads static serving with an authenticated, ownership-checked, traversal-safe /api/files route.
    • Added login and registration rate limiting, and rotated a JWT_SECRET that had been public in git history since the first commit.
    • Introduced Vitest in both packages (190 tests) and split the 542-line dashboard hook into a shared core plus five per-role hooks, cutting each command center from 13–32 props to 3–4.

  6. Phase 6: Panel Feedback — Category 1 (Database & Core Features)

    First of four categories from the capstone panel's defense feedback.

    • Added enrollment_status and study_load so Irregular and Dropout are modelled as two orthogonal axes rather than one overloaded column.
    • Multi-document requests: one selection, one payment, one combined total — with each document still routing through the desks independently.
    • Graduate Application module with an admin-configurable form; adding a question requires neither a migration nor a code change.
    • Moved document types and colleges into reference tables, making fees and availability admin-editable.
    • Hardened request creation: server-side pricing, and a student's request is always filed against their own record.
    • 284 automated tests (184 backend, 100 frontend); zero lint errors.

  7. Phase 7: Panel Feedback — Category 2 (Admin Maintenance & Analytics)

    Second of four categories from the panel's defense feedback.

    • Admin CRUD for Staff, Document Types and Colleges, where deletion is always a reversible deactivation.
    • Staff accounts issued with a single-use temporary password the user must replace at first login.
    • Report generation filtered by date range, status, document type and payment, with matching CSV export.
    • Student CSV export by category: Active, Graduates/Alumni, and Others (dropouts and transferees).
    • Efficiency analytics — turnaround per desk, end-to-end completion, throughput and staff workload — all derived from the audit trail.
    • 407 automated tests; zero lint errors.

  8. Phase 8: Panel Feedback — Category 3 (Payments & Notifications)

    Third of four categories from the panel's defense feedback.

    • Four admin-managed payment methods, behind a provider abstraction that leaves room for a hosted gateway.
    • Real-time in-app notifications over Socket.IO with an explicitly authenticated handshake — 55 ms measured end to end.
    • Diagnosed the “broken” SMS/email push as missing configuration, not a defect: placeholder SMTP credentials removed, channel health reported at startup, unconfigured channels skipped with a stated reason.
    • 438 automated tests; zero lint errors.
